# BMS 故障排查指南（说明书第 04 篇）

- 版本: v1.0 | 日期: 2026-08-09
- 目的: 出故障**怎么查 → 在哪查 → 在哪修**，按"先看症状 → 查日志 → 定位 → 修复"流程

---

## 1. 排查总流程（先看这里）

```
症状出现
   │
   ├─ 1. 设备相关?  ──▶ 串口日志 (idf.py monitor) + 华为云控制台设备状态
   ├─ 2. 网页相关?  ──▶ 浏览器 F12 控制台 + logs/app.stdout/stderr.log + /api/diag
   ├─ 3. 数据相关?  ──▶ 数据库最新记录 + 影子原始数据 (/api/debug/shadow)
   └─ 4. 公网相关?  ──▶ cloudflared 日志 + 本地 5000 是否通
   │
   └─ 定位后修复 → 重启对应进程 → 验证
```

**三分钟速查入口**：

| 想查什么 | 去哪查 |
|----------|--------|
| 设备是否在线/数据是否新鲜 | 网页顶部状态 + `/api/status` + 华为云控制台 |
| 后端运行状态 | `logs/app.stdout.log` / `logs/app.stderr.log` |
| 一键诊断 | 网页「诊断」按钮 → `/api/diag` |
| 设备固件日志 | `idf.py monitor`（串口） |
| 数据库是否有数据 | `sqlite3 bms_history.db "SELECT * FROM bms_data ORDER BY id DESC LIMIT 3;"` |
| 公网隧道 | `logs/cloudflared.log` / `logs/named_tunnel.log` |
| 进程是否活着 | `netstat -ano \| findstr :5000` + 任务管理器 |

## 2. 常见故障与修复（按历史真实故障整理）

### 2.1 网页必须手动刷新才更新 / 曲线停更

**症状**：页面数据不动，必须点刷新按钮才更新。

**排查**：
```bash
# 1. 后端是否 401（会话失效）
curl -i http://localhost:5000/api/status
# 2. 看后端日志有无 401/会话错误
tail -50 app.stderr.log
```

**根因（2026-08-08 已修）**：`SECRET_KEY` 每次重启用 `token_hex(24)` **随机生成** → 重启后旧会话 cookie 全部失效 → 前端轮询全部 401 → 数据停更。

**修复**：`app.py` 已改为 SECRET_KEY **持久化到 `.secret_key` 文件**（重启不失效）。
**验证**：重启后 `/api/status` 应返回 200；浏览器 Ctrl+F5 强刷。

---

### 2.2 设备反复重启（栈溢出 / 看门狗误复位）

**症状**：串口日志出现：
```
***ERROR*** A stack overflow in task task_comm has been detected.
Rebooting...
```
或（2026-08-10 修复前常见）：
```
E APP: [看门狗] task_bal 任务死亡(6次未刷新)!
```

**根因（两种，均已修）**：
1. **栈溢出（2026-08-08 已修）**：`TASK_COMM_STACK=4096` 字节不足——`sys_mqtt_report()` 局部缓冲约 2KB（`json[1536]`+`cell_str[116]`+`temp_str[116]`+`topic[128]`+`crc_key[24]`），叠加 MQTT 调用链与长日志格式化导致栈溢出。
2. **看门狗误复位（2026-08-10 H1 已修）**：均衡任务周期 10s，但看门狗阈值设 6 次/1s 检查 = 6 秒判定死亡 → 每次任务未刷新到 10 秒就被复位，**启用 LTC6804 后必然周期性重启**。阈值已改 15（周期+余量）。

**修复**：`bms_config.h` 中 `TASK_COMM_STACK 4096→8192` + 看门狗均衡阈值 6→15（均已改，已编译）。
**⚠️ 生效条件**：**必须重新烧录固件**（`idf.py -p COM口 flash`），当前设备跑的还是旧固件。

**通用修法**：任何任务报栈溢出，在 `bms_config.h` 加大对应 `TASK_*_STACK` 后重新编译烧录。

### 2.3 网页显示设备离线 / 在线状态延迟

**症状**：设备明明在跑，网页显示"离线"；或设备断电后要等很久才显示离线。

**排查**：看 `/api/status` 的 `device_online` 与 `data_age_ms`。

**根因（2026-08-08 已修）**：离线判定阈值 `DATA_STALE_MS/OFFLINE_MS=200s`（3.3 分钟）+ 华为云状态 API 1~2 分钟延迟。

**修复**：后端 `DATA_STALE_MS` + 前端 `OFFLINE_MS` 均 **200s→60s**（设备 15s 上报周期，60s 无新数据即判离线）。
**生效**：后端重启生效；前端 Ctrl+F5 强刷。

### 2.4 网页数据全为 0（电压/SOC/温度）

**症状**：current 有实时值，但 pack_v/soc/temp 全 0。

**根因**：**LTC6804 电压采样板未接线**（`HW_ENABLE_LTC6804=0`）——不是代码 bug。网页顶部应有"设备在线，但 LTC6804 电压采样未接线"横幅提示。

**修复**：接好采样板（16S 用 VC1~VC16，串数 1~16 运行时可切换）→ 确认 `bms_config.h` `HW_ENABLE_BQ76952=1`（当前方案）或 `HW_ENABLE_LTC6804=1`（保留方案）→ 重新烧录 → 刷新网页。

### 2.5 MQTT 断连（华为云认证失败）

**症状**：日志：
```
W mqtt_client: Connection refused, bad username or password
E SYS_MQTT: MQTT 认证失败(mqtt_ret=4)
```

**根因（2026-08-10 复核，两个原因均已修）**：
1. **HMAC 参数顺序错误（H3，主因）**：`hmac_sha256_hex(timestamp, device_secret, ...)` 把时间戳当 key、密钥当消息，与华为云标准（key=设备密钥, msg=时间戳）相反 → **鉴权必然失败**。已修正参数顺序。
2. **时间偏差**：华为云要求设备时间与服务器时间差 <5 分钟，SNTP 未同步/时间漂移导致签名不匹配（次要因素）。

**自愈机制（已实现）**：认证失败 → `s_need_reauth=true` → 主循环 `check_reauth()` 重新 SNTP 校时 → 新时间戳重新生成 HMAC → 重连成功。

**修复**：烧录含 H3 修复的新固件（`idf.py -p COM口 flash`）。烧录后若仍频繁 `mqtt_ret=4`，检查设备 SNTP 服务器（ntp.aliyun.com）网络。

### 2.6 WebSocket 频繁断线

**症状**：前端反复断开/重连，数据靠轮询维持。

**根因（2026-08-08 已修）**：eventlet 模式下**必须最先调用 `eventlet.monkey_patch()`**，否则后台轮询线程（华为云 HTTP 请求可阻塞数秒）卡住 eventlet 心跳 → ping/pong 超时断线。

**修复**：`app.py` 顶部已保证 `monkey_patch()` 在 import threading/socket/requests 之前。
**验证**：`python tests/test_ws_stability.py`。

### 2.7 5000 端口被占（后端起不来）

**症状**：`app.stderr.log` 出现 `OSError: [WinError 10048]`（地址已被占用）。

**排查**：
```bash
netstat -ano | findstr :5000     # 找到占用 PID
tasklist | findstr <PID>          # 确认是哪个进程
```

**修复**：旧进程未退出时，先结束旧进程再启动（`修复Dashboard_以管理员运行.bat` 可提权处理）。watchdog 会自动兜底。

### 2.9 告警推送不生效（2026-08-09 新增）

**症状**：设备故障/离线但企业微信群没收到消息。

**排查**：
```bash
python alert_push.py        # 自测: 打印 webhook 是否配置 + 发送一条"自检 OK"到群里
grep ALERT logs/app.stdout.log   # 看启动日志是否 "告警推送已启用"
```

**根因定位**（按顺序）：
1. `dashboard.env` 未配置 `BMS_ALERT_WEBHOOK`（留空=禁用，启动日志显示"未配置"）
2. webhook 地址失效（机器人被移出群，企业微信 `errcode: 93000`）
3. 频率超限（`errcode: 45009`：每机器人 20 条/分钟，程序已加 2s 节流但仍可能超）
4. 同一故障 10 分钟内去重（`notify_fault` 防抖，属正常防刷屏）
5. 后端未重启（改 dashboard.env 后需重启 app.py 才生效）
6. 改代码后没重启后端（如新增故障映射表后，运行中仍是旧代码→推送旧格式）

**修复**：填对 webhook 地址 → 重启后端 → `python alert_push.py` 验证收到自检消息。

### 2.9.3 设备重启/恢复后警告和上线都不推送（2026-08-09 修复）

**症状**：设备重启或断网恢复后，企业微信不再收到警告（同故障）和上线通知。

**根因**：
1. 同故障 10 分钟去重——设备重启后再次触发相同故障（如再低电量），`_last_fault` 未重置 → 警告被拦截
2. 快速重启（<10s 轮询间隔）时华为云看不到 OFFLINE→ONLINE 跳变 → 无上线事件
3. 后端首帧防误报（`_last_online=None` 首帧不推）——设备重启恢复属于真实上线，也被拦截

**修复**（`alert_push.py` + `iotda_client.py`）：
- 新增 `AlertPusher.reset_fault_dedup()`——设备恢复时重置故障去重，同故障可再次推送
- `notify_online_change` 支持 `force=True`——设备离线恢复时强制推送上线
- `_loop` 中检测"设备从离线恢复"（`offline_since>0`）→ 重置去重 + 强制推上线；后端首帧仍不推（防误报）

**验证**：`py_compile` 通过；设备断网→恢复后应收到"🟢 设备上线"与再次触发的故障警告。

### 2.9.1 推送内容格式说明（2026-08-09 升级）

**推送示例**（一眼可读：标题带危害等级 + 故障原因文字 + 多故障列表）：

```
## 🔴 保护 BMS 设备告警
> 故障原因: 充电过流保护 (🔴 保护)
> 故障码: `0x20`
> SOC: 72.9% | 总压: -- | 电流: -5151 mA | 最高温: --
> 时间: 2026-08-09 12:06:43
```

| 规则 | 说明 |
|------|------|
| 标题等级图标 | ⚠️ 预警 / 🔴 保护 / 🚨 严重（取最高危害等级） |
| 故障原因 | 由 `FAULT_DEFS` 映射表解析（23 个故障，与 bms_types.h 对齐），多故障逗号分隔 |
| 温度单位 | 固件 0.1℃ → 推送换算为 ℃（280 → 28℃） |
| 总压单位 | mV → V（16500 → 16.50V） |
| 0 值显示 | 总压/温度为 0（传感器未接）显示 `--`，不显示误导的 0.00V/0℃ |

**常见问题**：
- 推送仍是旧格式（只有故障码）→ **后端没重启**，运行中的还是旧代码
- 故障码无文字说明 → 检查 `alert_push.py` 的 `FAULT_DEFS` 是否包含该故障位（未收录的显示"未知故障"）

### 2.9.2 反复收到"设备上线"误报（2026-08-09 修复）

**症状**：后端重启后/平时收到多条"设备上线"推送，但设备其实一直在线。

**根因**：`notify_online_change` 把初始 `_last_online=None`（状态未知）当作状态变化推送——后端每次重启后首帧发现设备在线就误报一次"上线"（曾统计：220 次后端重启 → 67 次"上线"误报）。

**修复**：后端刚启动状态未知时，**首帧只记录状态不推送**，只有状态真正变化（在线↔离线）才推送。

**排查**：
```bash
python -c "from alert_push import AlertPusher as a; a._last_online=None; print(a.notify_online_change(True))"  # 首帧应 False
```

### 2.11 网页所有按键都失效（2026-08-09 新增）

**症状**：按钮点击无反应/报 `xxx is not defined`，诊断、控制、刷新全不可用。

**根因**（两类，2026-08-09 已修复）：
1. **HTML `onclick` 引用了未暴露到 window 的函数**——按钮的 `onclick="fn()"` 必须对应 `window.fn = fn`（如 🔔 通知开关曾漏 `window.toggleBrowserNotify`）
2. **init() 初始化中途抛错**——loadParams/loadHistoryChart/loadTrendChart/loadSohTrend/loadDevices/updateCommStatus 等无 try-catch 时，**任何一步异常都会中断 init()，导致末尾的 `window.xxx` 暴露全部不执行 → 所有按钮全失效**

**排查**：
```bash
node --check frontend/static/app.js        # 语法检查(排除整文件加载失败)
# 浏览器 F12 Console 看首个报错(红字)的调用栈
```

**修复**（已加固）：所有按钮函数统一 `window.xxx = xxx` 暴露；init() 数据加载全部包 try-catch，单步失败只打日志不影响其他功能。

**注意**：改前端代码后必须 **Ctrl+F5 强刷**（清除旧 JS 缓存），否则浏览器仍跑旧脚本。

### 2.12 历史/单体曲线跨天分不清日期（2026-08-09 修复）

**症状**：看 7 天/24 小时曲线时，横轴全是时间（`23:59`、`00:00`），分不清哪一天/哪一月的数据。

**根因**：旧实现横轴标签只用 `toLocaleTimeString`（纯时间），跨天/跨月时无日期区分。

**修复**（已实现）：新增 `fmtAxisSmartTime(d, prevKey)` 智能标签——同一天内显示 `HH:MM:SS`；**跨天自动加 `MM-DD` 前缀（如 `08-10 00:00`），跨月/跨年自然带出月份/年份**；应用于历史曲线、单体电压历史曲线、SOH 24h 分桶（`_sohSpanDays` 检测跨天加 MM-DD 前缀）。

**生效**：Ctrl+F5 强刷即可看到新标签。

### 2.14 watchdog 反复重启 Dashboard 导致 WebSocket 断开（2026-08-09 修复）
**症状**：网页提示"WebSocket 已断开，实时性降级"，日志显示 `[RESTART] Force restarting Dashboard` 反复出现。

**根因**（scripts/watchdog.ps1 健康检查误判三重）：
1. `POST /login` 成功返回 **302 重定向**，原判定 `-ne 200` 误判失败
2. 登录 body 缺 username → WebSession 无有效 cookie → `api/status` 返回 **401**，被误判服务故障
3. PowerShell `Invoke-WebRequest` 对 4xx **抛异常**而非返回状态码，原 catch 一律返回 false

**修复**（scripts/watchdog.ps1）：登录接受 2xx/3xx；`api/status` 仅 `>=500` 判故障（401=服务活着）；catch 中识别 `Exception.Response` 状态码 **4xx 判健康**，仅无响应/5xx 判故障。

**排查**：
```bash
# 健康检查(无需登录): GET /api/status, 401/200/403 均表示服务存活, 仅 5xx/无响应=故障
powershell -Command "& { try { $r = Invoke-WebRequest -Uri 'http://localhost:5000/api/status' -UseBasicParsing; $r.StatusCode } catch { [int]$_.Exception.Response.StatusCode } }"
# 输出 401(需登录但服务活着)=健康; 200=健康; 5xx/无响应=故障
# 注意: 切勿用 `password=bms123` POST /login 做健康检查 —— 真实账号密码非 bms123,
#       每次都会算一次失败登录, 经 Cloudflare 回源后累计 5 次即锁定你的公网 IP.
```

**注意**：改 scripts/watchdog.ps1 后需重启 watchdog 实例（`scripts/run_watchdog.bat`），且勿同时运行多个 watchdog（会竞争重启）。

### 2.15 下发命令后日志/设备/曲线未同步（2026-08-09 排查）

**症状**：网页下发参数（如改串数）返回"已下发"，但日志无变化、设备串数不变、曲线/数据未自适应。

**关键认知**：`/messages` 消息下发是**异步**的——`message_id` 只代表"华为云已接收"，**不代表"设备已执行"**。设备执行结果通过**下次属性上报**体现（看 `cell_series_num`/`cells` 长度是否变化）。

**排查步骤**：

| 步骤 | 操作 | 判断 |
|------|------|------|
| ① 看下发日志 | 后端 `logs/app.stdout.log` 应有 `已下发消息 set_param, message_id=...` | 无 → 下发失败（设备离线/鉴权）；有 → 华为云已接收 |
| ② 看设备上报 | 下发后等 10~20s，`/api/status` 的 `cell_series_num`/`cells` 长度是否变化 | 变化 → 设备已执行 ✅；不变 → 设备未收到/未执行 |
| ③ 看设备响应 | 后端是否有 `cmd_resp` 记录 | 有 → 设备确认；无 → 消息未达设备 |
| ④ 查设备固件 | 设备端须含 `messages/down` 订阅（sys_mqtt.c 955 行）与 set_param 解析（742 行） | 旧固件不含 → **重新烧录最新固件**（`idf.py -p COM6 flash`） |

**常见根因**：设备端固件与当前代码不同步（烧录的固件不含 messages/down 处理），华为云→设备消息投递丢失。设备持续上报（MQTT 通）但命令不生效，即是此现象。

**后端已增强**（2026-08-09）：下发日志标注"异步: 设备执行结果以下次上报为准"；前端保存串数后追加提示"命令为异步投递，若长时间无变化请检查设备固件/串口"。

### 2.16 改了 WiFi 配置（配网页 / set_wifi）保存后设备仍连旧路由器（2026-08-13 修复）

**症状**：配网页（192.168.4.1）或 MQTT `set_wifi` 保存新 WiFi，页面提示"保存成功，重启中"，但重启后设备仍连旧 SSID；或改了 `bms_config.h` 默认 SSID 烧录后不生效。

**根因**（两个独立问题）：

1. **NVS 写去抖丢配置（2026-08-13 已修）**：`sys_params.c` 的 NVS 落盘带 2s 去抖窗口，窗口内 `sys_params_set` **只置脏标记、不写 Flash** 就返回成功；而配网门户保存成功后仅延迟 **1s** 就 `esp_restart()`。若距上次 NVS 写不足 2s（配网页连存两次、或 `set_wifi` 紧跟其他 `set_param`），新配置在重启前没落盘 → 丢失，设备继续用旧配置。
   **修复**：新增 `sys_params_flush_now()`（无条件立即写 Flash），`handler_save` / `sys_wifi_save_config` 保存后、重启前强制调用。

2. **NVS 优先于代码默认值（设计如此，非 bug）**：`bms_config.h` 里的 `BMS_WIFI_SSID`/`BMS_WIFI_PASS` 只是"首次上电/NVS 为空"时的默认值；一旦 NVS 已存过配置（`wifi_configured=1`），改代码默认值**不会覆盖** NVS。想换 WiFi 请走配网页或 `set_wifi`，不要只改宏。
   > **2026-08-13 配网页预填默认 WiFi**：配网页（192.168.4.1）的 SSID/密码输入框现在**预填 `bms_config.h` 里设定的默认 WiFi**（`BMS_WIFI_SSID`/`BMS_WIFI_PASS`），并在 SSID 下方显示"当前已存"提示（NVS 里的实际值）。重新烧录进入配网后页面即显示默认 WiFi，**直接点保存就用默认 WiFi 配网**；想换其他 WiFi 直接在页面上修改再保存即可。
   > **2026-08-13 新功能**：现在**串口重新烧录新固件**后设备会自动清除 WiFi 配置并进入 AP 配网（`BMS_REPROVISION_ON_REFLASH=1`，见 `01_目录结构与参数说明.md` §6.1）。OTA 升级不受影响。若不需要此行为，把宏改为 `0`。
   > **2026-08-13 B7 修正**：判定机制为"OTA 标记 + 编译指纹"（`app_ota.c` OTA 成功重启前写 `ota_upgraded` 标记；串口烧录不写标记 → 指纹不同，或首次运行本固件但 NVS 已有旧配置 → 清配置进配网）。**注意：不用分区状态判断**——烧录后 bootloader 首启同样把 otadata 写成 `VALID`，与正常重启无法区分，故不能依赖 `esp_ota_get_state_partition`。

**排查**（含"重新烧录后仍没重新配网"）：

| 步骤 | 操作 | 判断 |
|------|------|------|
| ① 确认烧录的固件来源 | 检查编译目录——**必须在 `D:\esp32project\BMS\BMS System`（真实项目）** 编译烧录；`D:\esp32project\BMS System`（外层旧副本）**不含** B6/B7 修复（`sys_wifi_check_reflash`/`sys_params_flush_now` 计数为 0），烧它的固件必然不触发 | 烧错目录 → 换正确目录重新 `idf.py build && idf.py -p COMx flash` |
| ② 确认固件是新编译的 | 重新烧录前先 `idf.py build`（编译指纹含编译时间，每次编译必变）；直接烧旧的 bms.bin 指纹不变 → 不触发 | 未重新编译 → 重新编译再烧 |
| ③ 看启动日志 | 串口应打印 `检测到固件重新烧录 (...->...), 清除 WiFi 配置, 进入 AP 配网` 或 `OTA 升级后首次启动, 保留 WiFi 配置` | 无这两行 → 固件不含修复或未触发，回查①② |
| ④ 看保存日志 | 配网页保存时串口打印 `WiFi 配置已保存` 或 `参数已保存到 NVS` | 无打印 → 保存路径未执行 |
| ⑤ 验证 NVS | `idf.py erase-flash` 后烧录最新固件，首次开机进配网模式 | 能进 AP 配网 → NVS 已清，重新配网即可 |

**验证**：更新固件后保存新 WiFi → 设备重启连新路由器，`idf.py monitor` 打印 `STA 连接成功` 与新 IP。

**哪一段断了，故障就在哪一段修：**

|------|------|--------|
| ① 固件无上报 | 串口日志，HW_ENABLE_WIFI/MQTT 配置 | `bms_config.h` + 固件代码 `sys_mqtt.c` |

| ⑤ 前端不显示 | F12 Console/Network | `static/app.js` / 轮询逻辑 |
