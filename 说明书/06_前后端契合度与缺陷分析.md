# 06 · 固件 ↔ 前端/后端 契合度与缺陷分析

> 分析对象：ESP32 BMS 固件（`components/`）与 Web 监控台（`tools/dashboard/`：Flask 后端 `app.py` / `iotda_client.py` + 前端 `static/app.js`）。
> 通信方式：华为云 IoTDA MQTT（`commands/#` 与 `messages/down` 两条主题）+ 前端经 HTTP `/api/*` 调后端、后端经 `/messages` API 下发。
> 结论（2026-08-09 初版）：存在 2 个阻断级（BLOCKING）缺陷 + 若干数据正确性/一致性与文档漂移问题。遥测字段/单位本身一致，无错配。
> **2026-08-10 复核**：**D2（set_param 被拒）已修复**（固件 `handle_set_param` 改用 `cmd_get_field` 兼容 paras 内层，sys_mqtt.c:211-212）；**D1（控制命令 enable 丢失）已修复**（后端 `/api/cmd` 顶层参数并入 `paras` + 前端 `sendDeviceCmd` 改发 paras 子对象）；**D3（假成功回比）已修复**（前端命令/参数下发后回比确认，见 §三）；**D4（SOC 算法标签缺 3/4）已修复**（app.js:4396 补齐 5 档）；**D5（头文件漂移）已修复**（sys_mqtt.h 注释与华为云 Topic 对齐）；**D6（CRC 未消费）已修复**（固件 crc_key 与上报字段对齐 + 后端复算校验 `crc_ok` + 前端状态展示）。

## 一、根因：参数放置约定三处不一致

固件对“命令参数应放 `paras` 还是消息顶层”存在两套互相打架的约定：

| 层 | 期望的参数位置 |
|---|---|
| 前端 `sendDeviceCmd` | body **顶层**（`Object.assign({cmd}, paras)`，`app.js:2427`） |
| 后端 `publish_cmd` | 只认 `paras`/`args`，顶层字段被丢弃（`iotda_client.py:916`） |
| 固件 `handle_command`(`commands/#`) | `cmd_get_field` 先查 `paras` 再查顶层（`app_tasks.c` `cmd_get_field`） |
| 固件 `handle_device_message`(`messages/down`) | 控制命令会把 `paras` 合并到顶层（sys_mqtt.c:782-788）；但 `set_param` 分支却从**顶层**读 `key/value`（sys_mqtt.c:743-744） |

后端 Bug7 修复后**所有命令改走 `messages/down`**（`iotda_client.py:911`），但固件 `messages/down` 路径的 `set_param` 处理读错层级，而 `handle_set_param` 本身也只认顶层 → 自相矛盾。

## 二、阻断级缺陷（必须修）

### D1. 远程控制命令全部失效（set_charge / set_discharge / set_balance / set_relay）【✅ 2026-08-10 已修复】
- **链路（修复前）**：前端 `toggleSwitch` → `sendDeviceCmd` 发 `{cmd, enable:<bool>}`（顶层平铺，旧 `app.js:2880` `Object.assign({cmd}, paras)`）→ 后端 `/api/cmd` 把整个 payload 原样传给 `publish_cmd`（旧 `app.py:1217`，未把 `enable/charge/discharge/mask` 收进 `paras`）→ `publish_cmd` 只取 `paras`/`args`（不存在）→ 下发 `{cmd, paras:{}, timestamp}` → 固件 `cmd_get_field(root,"enable")` 先查 `paras`（空）再查顶层（无）→ **默认 false**。
- **后果**：网页切换充电 MOS / 放电 MOS / 均衡 / 主继电器，**永远只能关、无法远程开启**（`enable` 恒为 false）。属于安全/控制反向失效，最高优先级。
- **修复（2026-08-10，前后端双保险）**：
  1. 后端 `app.py` `/api/cmd`：新增参数归一化——把顶层非元字段（`cmd/command_name/timestamp/paras/args` 之外）**并入 `paras`** 再下发，兼容"顶层平铺"与"paras 子对象"两种格式；
  2. 前端 `app.js` `sendDeviceCmd`：改为 `{cmd, paras:{...}}` 规范格式，与 `switch_battery`、`/api/params` 的 paras 用法统一。
  - 两端独立生效、互不依赖：旧前端/原始 JSON 输入框走顶层也能被后端兜底归一化；新前端即使后端未更新也能正确透传。

### D2. 参数下发（set_param）被设备静默拒绝（所有保护阈值 / 串数 / SOC 偏移增益等）【✅ 2026-08-10 已修复】
- **链路（修复前）**：前端 `/api/params` 发 `{cmd:"set_param", paras:{key,value}}`（`app.py:1269`）→ `publish_cmd` 正确透传 `paras` → 设备旧固件从顶层读 `key/value` 取不到 → `send_cmd_resp("set_param", false)`。
- **修复**：2026-08-10 固件 `sys_mqtt.c` 新增 `cmd_get_field`（优先查 `paras` 子对象，fallback 顶层，sys_mqtt.c:198-206），`handle_set_param` 已改用（sys_mqtt.c:211-212）→ 参数下发已打通（含串数/容量/保护阈值）。
- **生效条件**：需将含此修复的新固件烧录到设备。

## 三、数据正确性 / 状态误报

### D3. “下发成功”与实际执行脱节（假成功）【✅ 2026-08-10 已修复】
- `publish_cmd` 在华为云返回 `message_id` 即返回 `ok=True`，前端据此显示“已下发成功”。但 `/messages` 为异步、无执行回执，设备可能根本没执行。
- **修复（2026-08-10，前端回比机制）**：
  1. 控制命令：`sendDeviceCmd` 下发成功后登记期望状态（`set_charge→charge_mos`、`set_discharge→discharge_mos`、`set_balance→balance_on`、`set_relay→charge+discharge`），`updateKPI` 在下次属性上报中比对，15s 内匹配 → “✅ 设备已确认执行”，超时未变 → “⚠️ 设备未响应/执行失败” + toast 提示（app.js `_registerCmdVerify`/`_checkCmdVerify`）。
  2. 参数命令：`saveThresholds` 成功后登记期望键值，`loadParams` 回显时比对 `_checkParamVerify`，未确认生效同样提示。
- **生效条件**：前端 Ctrl+F5 强刷。

## 四、一致性 / 文档漂移（非阻断，但易引发误读）

### D4. SOC 算法回显标签缺 3/4 两档【✅ 2026-08-10 已修复】
- 下发映射覆盖 5 档（`app.js:3295`，`algoIdx` 0~4 全有，与固件 `soc_algo=0..4` 一致）。
- 修复前回显 `ALGO_NAMES` 仅 0/1/2（`app.js:4345`）→ 设备上报 `soc_algo=3`(MCC-EKF) / `4`(UKF) 时显示 `undefined` 或原始数字。
- **修复（2026-08-10）**：`ALGO_NAMES` 补齐 5 档并统一索引 0 名称为 “AEKF双卡尔曼”（与发送标签 `algoIdx` 一致，原为 “安时积分+卡尔曼”）——`{0:"AEKF双卡尔曼", 1:"纯安时积分", 2:"开路电压法", 3:"MCC-EKF(默认最优)", 4:"UKF无迹卡尔曼"}`，与下拉 `<option>` 文本逐字一致，select 可正确回显。

### D5. 头文件/文档与实现漂移【✅ 2026-08-10 已修复】
- 修复前 `sys_mqtt.h` 描述的是旧 `bms/cmd`、`bms/data` Topic 及“set_wifi 不需要回调”等，与 `sys_mqtt.c` 实际华为云 Topic 不符。
- **修复（2026-08-10）**：`sys_mqtt.h` 头部注释更新为华为云 IoTDA 原生 Topic（`properties/report` / `events/up` / `commands/#` / `messages/down` / `properties/set/#` / `commands/response`）+ HMAC 鉴权说明；`sys_mqtt_init` 注释改为“订阅 commands/#、messages/down、properties/set/# 三个下行主题”；`register_cmd_callback` 说明同步内置命令范围（含 set_charge/set_discharge/set_balance/set_relay）。
- 遗留说明：`set_wifi` 在白名单（`app.py:286`）但前端从未调用，属“死命令”但实现正确，保留。

### D6. CRC 完整性校验未被消费【✅ 2026-08-10 已修复】
- 固件上报尾部追加安全 `crc`/`crc32`（功能安全项 S1b），修复前 Web 端从不读取/校验。
- **修复（2026-08-10，固件+后端+前端全链路闭环）**：
  1. 固件 `sys_mqtt.c`：crc_key 由 `bmask` 原始 2 字节改为上报的 `balanceOn` 布尔 → crc_key 与上报 JSON 字段一一对应（fault/chargeMos/dischargeMos/balanceOn/workState/chargeMode/timestamp 共 11 字节），后端可精确复算；
  2. 后端 `iotda_client.py`：新增 `verify_report_crc()`（与固件同算法 CRC8 多项式 0x07 + IEEE CRC32 0xEDB88320），`_shadow_to_payload` 复算比对并输出 `crc_ok`（True/False/None=旧固件未上报），失败时打印告警日志；
  3. 前端：顶部状态栏新增 `crcStatus` 徽章（`index.html` + `updateKPI`），显示 “CRC完整/CRC异常/CRC旧固件”。
- **生效条件**：需烧录含新 crc_key 布局的固件；旧固件显示 “CRC旧固件” 属预期。

## 八、2026-08-10 契合度复核 · 三方全链路核查结论

> 对"固件上报字段 ↔ 后端解析 ↔ 前端消费""命令/参数/故障码/CRC/串数"五条契约做了全量比对（自动化差集 + 人工复核）。

### 8.1 上报字段链路 ✅ 一致（1 处物模型缺口已修复）

| 项 | 结论 |
|----|------|
| 物模型标识符 | 华为云物模型 `property_id`（在线 JSON）与 `propertyName`（V2 zip）均为**英文短名**（soc/vMax/packV/cellVoltages/chargeMos...），中文只是显示名 → 与固件上报完全一致 |
| 固件上报 27 字段 | 与 V2 物模型 **100% 覆盖**（差集验证通过，crc/crc32 补入后无遗漏） |
| 后端解析 | `_shadow_to_payload` 同时兼容 camelCase 新字段 + snake_case 旧字段，与物模型对齐 |
| 单位换算 | mV→V、mA→A、0.1℃→℃、SOC 0~1→% 全链路一致（前端/后端/固件三方核对） |
| 🔧 本次修复 | **在线 JSON 20→22 属性、V2 zip 48→50 属性，补入 `crc`/`crc32`**（原 D6 固件已上报但物模型未定义 → 华为云影子不存、后端永远取不到 → 校验形同虚设；补齐后 D6 真闭环） |

### 8.2 命令下发链路 ✅ 一致

- 前端实际调用命令（set_charge/set_discharge/set_balance/set_relay/clear_alarm/restart/get_info/ota_check/ota_upgrade/reset_params/switch_battery）全部在 `ALLOWED_CMDS` 白名单内；
- 固件 `messages/down` 大写匹配（SET_CHARGE/SET_PARAM/GET_INFO/SWITCH_BATTERY...）+ 回调命令（CLEAR_ALARM/RESTART/OTA_*）全部对齐；
- 控制命令参数经 2026-08-10 D1 修复后走 `paras` 子对象，固件 `cmd_get_field` 兼容两层 → 链路贯通。

### 8.3 参数键链路 ✅ 一致

- 后端 `PARAM_META` **41 键** ↔ 固件 `handle_set_param` **43 键**（差集 = 0 缺；固件多 `soc_gain`/`soc_offset` 属扩展项）；
- 上下限/单位已按 1~32S 修正，default 与 bms_config.h 一致。

### 8.4 故障码映射 ✅ 三方完全一致

- 固件 24 个（含 FAULT_NONE=0x0）；后端 `FAULT_DEFS` 23 个、前端 `FAULT_MAP` 23 个 → 逐位差集为 **0**，含绝缘 2 码（0x200000/0x400000）全对齐。

### 8.5 CRC 链路与串数自适应 ✅ 闭环

| 链路 | 结论 |
|------|------|
| CRC | 固件 crc_key 与上报字段一一对应 → 物模型（本次补齐）→ 影子 → 后端 `verify_report_crc` 复算输出 `crc_ok` → 前端 `crcStatus` 徽章，全链路闭环 |

### 8.6 复核结论

**前后端与固件契合度：达标 ✅**（此前 D1~D6、F1~F5 及本轮物模型缺口修复后，五条契约全部对齐，无遗留错配）。
