## 二、固件修复明细（B1–B5）

### B1 / B2 — MQTT 共享状态跨任务互斥（中危，最关键）
文件：`components/bms_middleware/sys_mqtt.c`

**根因**：`s_client` / `s_connected` / `s_last_command_id` 由 MQTT 事件任务（写）与 task_comm / 上报任务（读并 publish）并发访问。认证失败后 `sys_mqtt_check_reauth` 会 `destroy` 旧 client 再 `init` 新 client，若此时上报线程读到已销毁的 `s_client` → use-after-free 崩溃；`s_last_command_id` 并发读写产生撕裂读。

**修复**：
- 新增 `s_state_mutex`（互斥锁，在 `sys_mqtt_init` 中 `xSemaphoreCreateMutex()`，仅一次）。
- `publish_json()` 改为在**锁内**校验 `s_connected && s_client != NULL` 后再发布，返回是否发布成功（供 `sys_mqtt_report` 决定缓存还是发布）。
- `cache_replay_send_func()` 同样在锁内校验 `s_client`。
- `send_cmd_resp()` 在锁内读取并清空 `s_last_command_id`（且必须在调用 `publish_json` 前释放锁，避免非递归互斥量递归死锁）。
- `handle_get_info()` 的 `mqtt_connected` 与 `s_last_command_id` 读取均改为锁内。
- 事件回调 `MQTT_EVENT_CONNECTED/DISCONNECTED`、`sys_mqtt_stop`、`sys_mqtt_is_connected` 的 `s_connected` 读写均加锁。
- **重建路径改为"锁内置空 + 锁外本地销毁"**：
  ```c
  MQTT_STATE_LOCK();
  esp_mqtt_client_handle_t old_client = s_client;
  s_client = NULL;          // 立即置空, 并发 publish 看到 NULL 直接跳过
  s_connected = false;
  MQTT_STATE_UNLOCK();
  if (old_client != NULL) { esp_mqtt_client_destroy(old_client); ... }
  ```
  彻底消除"读已销毁句柄"的窗口。

### B3 — 继电器 set 与 remote_override 非原子（低危）
文件：`components/bms_app/app_tasks.c`（SET_CHARGE / SET_DISCHARGE / SET_RELAY）、`components/bms_middleware/sys_mqtt.c`（handle_property_set 的 chargeEnable / dischargeEnable / relayCharge / relayDischarge，共 4 处）

**根因**：`set_relay()` 与 `set_remote_override(true)` 顺序为"先设继器、后开 30s 覆盖保护"，二者之间存在窗口，保护任务可能用自身逻辑覆盖刚下发的继电器状态。

**修复**：将 `sys_data_set_remote_override(true)` **前置**到 `set_relay` 之前。6 处命令路径统一修复。

### B4 — LTC6804 多芯片温度失明（硬件相关）
文件：`components/bms_bsp/bsp_ltc6804.c`、`components/bms_bsp/include/bsp_ltc6804.h`、`components/bms_app/app_tasks.c`

**根因**：`bsp_ltc6804_read_gpio()` 硬编码只从 `chip 0` 读 GPIO（NTC 分压），多芯片级联且 NTC 接在其他片时温度保护失明。

**修复**：遍历所有 `s_inited[ch]` 芯片，每片 GPIO1~GPIO5 写入 `gpio_mv[ch*5 + i]`；调用方 `app_tasks.c` 缓冲改为 `gpio_mv[LTC6804_CHIP_NUM * 5]`，遍历上限同步为 `LTC6804_CHIP_NUM * 5`。
- **单芯片（`LTC6804_CHIP_NUM=1`，默认配置）行为完全不变**（仅 chip0，offset 0）。
- 多芯片时自动支持每片独立 NTC 测温，不溢出调用方缓冲。
- 无已初始化芯片时返回 `BMS_ERR_FAIL`（原 `!s_inited[0]` 的 `PARAM_INVALID` 语义调整为更贴切的 FAIL）。

### B5 — `cell_dv` 无符号下溢（防御性）
文件：`components/bms_app/app_protection.c:442`

**根因**：`uint16_t cell_dv = pack->cell_mv_max - pack->cell_mv_min;` 若因任务非原子导致 `min > max`，无符号下溢回绕成极大值，误报压差过大。

**修复**：
```c
uint16_t cell_dv = (pack->cell_mv_max > pack->cell_mv_min)
                   ? (uint16_t)(pack->cell_mv_max - pack->cell_mv_min)
                   : (uint16_t)(pack->cell_mv_min - pack->cell_mv_max);
```

## 一、B6【中危】保存 WiFi 配置后立即重启 → 新配置丢失，设备继续连旧路由器

- **文件**：`components/bms_middleware/sys_params.c`（`params_commit` / 新增 `sys_params_flush_now`）、`sys_config_portal.c`（`handler_save`）、`sys_wifi.c`（`sys_wifi_save_config`）、`include/sys_params.h`
- **根因**：`params_commit` 的 NVS 写去抖（`PARAMS_NVS_COALESCE_MS=2000ms`）在窗口内**只置脏标记、不落盘**即返回 `BMS_OK`；而配网门户 `handler_save` 收到 OK 后仅延迟 **1s** 就 `esp_restart()`。若距上次 NVS 写不足 2s（例如配网页连存两次、或 MQTT `set_wifi` 紧跟其他 `set_param`），脏数据尚未刷进 Flash 便重启 → 新 SSID/密码丢失，设备继续用旧配置连旧路由器。MQTT `set_wifi`（`sys_mqtt.c` 两处）路径同理。
- **修复**：新增 `sys_params_flush_now()`——无条件把活动缓冲写 Flash（无视去抖窗口，全程持锁）；在 `handler_save`、`sys_wifi_save_config` 保存成功后、重启前显式调用。
- **验证**：ESP-IDF v5.2.7 编译通过（`Project build complete`，`bms.bin` 生成）。

## 三、新功能：重新烧录自动重新配网（B7，2026-08-13）

> 用户指令：**设置成当重新烧录时重新配网**（OTA 升级不受影响）。

- **文件**：`bms_config.h`（`BMS_REPROVISION_ON_REFLASH`）、`sys_wifi.c`（新增 `sys_wifi_check_reflash()`）、`sys_params.c/h`（新增 `sys_params_get/set_reflash_fp()`）、`app_tasks.c`（STA/AP 决策前调用）、`bms_middleware/CMakeLists.txt`（补 `app_update`/`esp_app_format` 依赖）、`sys_params.h`（补 `#include <stddef.h>`）
- **方案**：运行分区 OTA 状态 + 编译指纹双信号判定——
  1. `esp_ota_get_state_partition()` 返回 `PENDING_VERIFY` → OTA 升级后首启 → **保留** WiFi 配置，仅刷新指纹；
  2. 否则比对 NVS 中记录的编译指纹（`BMS_FIRMWARE_VERSION + __DATE__ + __TIME__`，每次编译必变）：不同 → 串口重新烧录 → `sys_wifi_clear_config()` + `sys_params_flush_now()`，下次启动进 AP 配网；
  3. 相同 → 正常重启，不动。
- **验证**：ESP-IDF v5.2.7 编译通过（`Project build complete`，bms.bin 生成，app 分区余 84%）。说明见 `01_目录结构与参数说明.md` §6.1。

## 四、B7 方案修正（2026-08-13 同日，实机反馈"烧录后仍连旧 WiFi 且无法配网"）

> 用户反馈：烧录设备后仍连旧 WiFi，且无法配网。

- **B7 原方案缺陷**：用 `esp_ota_get_state_partition()==PENDING_VERIFY` 判断"OTA 升级后首启"以保留配置——但实测 **串口烧录（`idf.py flash`）会把 otadata 分区清空（`ota_data_initial.bin` 全 0xFF），且项目启用 `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`，bootloader 首次启动同样把运行分区置为 `PENDING_VERIFY`** → 烧录被误判为 OTA → 保留旧配置不配网；叠加首次烧录 B7 固件时 NVS 无 `reflash_fp` 记录（`get` 返回 STORAGE，原代码走"首次上电"分支不动作）→ 两个原因叠加导致 B7 完全不触发。
- **修复**：
  1. **改用显式 OTA 标记**：`app_ota.c` 两条 OTA 成功路径（`app_ota_check_and_upgrade` / `app_ota_upgrade_with_url`）在 `esp_restart()` 前调用 `sys_params_set_ota_upgraded()` 写 NVS `ota_upgraded=1`。
  2. `sys_wifi_check_reflash()` 重写判定：
     - `sys_params_is_ota_upgraded()` 为真 → OTA 首启 → **保留** WiFi 配置，`clear_ota_upgraded()` 消费标记，刷新指纹；
     - 否则比对 `reflash_fp` 指纹：不同 → 串口重新烧录 → 清配置进配网；
     - **新增兜底**：无指纹记录但 NVS 已有 `wifi_configured=1`（旧固件遗留配置）→ 同样清配置重配网（解决首次烧录 B7 固件不触发的问题）。
  3. 移除 `sys_wifi.c` 对 `esp_ota_ops.h`/`esp_app_format.h` 的依赖（不再用分区状态判断）。
- **文件**：`sys_params.c/h`（新增 `set/is/clear_ota_upgraded`）、`sys_wifi.c`（重写 `sys_wifi_check_reflash`）、`app_ota.c`（OTA 成功路径写标记）。
- **验证**：ESP-IDF v5.2.7 编译通过（`Project build complete`，bms.bin 生成，app 分区余 84%）。
